# Техническая разведка TaskHero (TaskGamer) — карта для следующих этапов

Дата: 2026-08-28. Ветка: `develop`, HEAD `6becc1d` («feat: v2»). Продуктовый код не менялся — это только разведка и карта для следующей итерации.

Контекст: `prompt.txt` в корне репозитория — исходное ТЗ (от 27.08.2026, автор Дима Васильев), по которому сделан коммит `feat: v2`. Оно содержит 28 пронумерованных разделов и явно требует идемпотентности начисления награды (§3), исправления «Ошибки назначения задания» (§4) и корректной работы часового пояса в повторах (§14). Ниже показано, что часть этих требований технически не выполнена, несмотря на код и тесты, которые утверждают обратное.

---

## 1. Краткая архитектура

Мультимодульный Maven/Spring Boot 3.4 проект, Java 21, PostgreSQL 16 + Liquibase, MapStruct, JWT.

- `common` — `BaseEntity` (UUID id, createdAt/updatedAt, **без `@Version`** — оптимистичных блокировок в проекте нет вообще), enums, `GlobalExceptionHandler`.
- `user-service` (:8081) — родители, дети, магазин, награды за уровни, JWT-аутентификация.
- `task-service` (:8082) — шаблоны заданий, назначения, начисление EXP/монет (через Feign в user-service), планировщики (истечение дедлайна, генерация повторов).
- `app` (:8080) — Thymeleaf BFF, Feign-клиенты к обоим сервисам, вся серверная валидация форм.
- Три отдельных процесса/БД, вызовы между ними — синхронный REST через OpenFeign, **без распределённых транзакций, saga или outbox**.
- Ни в одном Dockerfile/compose/application.yml не задан `TZ` — все три JVM работают в дефолтной зоне контейнера (обычно UTC), при этом миграция `010-store-due-date-as-utc-instant.xml` явно хардкодит `Europe/Moscow` для конвертации старых данных. Это системное расхождение — ключевая причина большинства найденных багов.
- **Уточнение от заказчика**: реальные семьи-пользователи живут в разных часовых поясах РФ/СНГ — значит фикс дат/повторов должен хранить часовой пояс семьи в модели (`Parent`), а не жёстко фиксировать один `TZ` на контейнерах.

## 3. Фактический жизненный цикл задания (прослежен по коду, не по названиям)

```
Родитель [ParentController.assignTask, /parent/assign]
  ├─ если templateId не передан → taskServiceClient.createTemplate(...) [создаёт TaskTemplate СРАЗУ]
  ├─ FormDateTimeParser.parseToInstant(dueDate) [парсит ПОСЛЕ создания шаблона]
  └─ taskServiceClient.assignTask(...) → TaskAssignmentServiceImpl.assign()
        ├─ проверка: шаблон принадлежит родителю, активен, нет активного назначения (если не repeatable)
        ├─ save(TaskAssignment{status=CREATED, dueDate})
        └─ если template.autoSubmit → сразу status=APPROVED + grantReward() (минуя SUBMITTED)

Ребёнок [TaskAssignmentServiceImpl.submit()]
  ├─ findByIdWithTemplateForUpdate (PESSIMISTIC_WRITE)
  ├─ проверка status==CREATED, dueDate не в прошлом
  ├─ save(status=SUBMITTED, submittedAt)
  └─ если introTask → сразу APPROVED + grantReward() + unlockNickname() (минуя обычное подтверждение)

Родитель [approve()/reject()]
  ├─ findByIdWithTemplateForUpdate (PESSIMISTIC_WRITE) — блокирует строку на время транзакции
  ├─ проверка status==SUBMITTED
  ├─ save(status=APPROVED/REJECTED, reviewedAt, expEarned, coinsEarned)
  └─ approve(): rewardService.grantReward() → Feign PUT user-service /children/{id}/reward
        └─ ChildServiceImpl.addReward(): child.exp+=exp; child.coins+=coins; пересчёт level;
           если level вырос → LevelRewardService.checkAndClaimRewards()
           save(child) — БЕЗ версии/блокировки, обычный UPDATE

Фоновые процессы:
  DeadlineExpirationScheduler (раз в час): CREATED + dueDate<now → EXPIRED
  RecurringAssignmentScheduler (раз в час): для repeatable-шаблонов считает "сегодня" по
    ZoneId.systemDefault(), сверяет с RecurrenceHelper.getNextOccurrences(anchor=дата первого
    назначения), если совпадает и ещё не создано — новое TaskAssignment{CREATED, dueDate=23:59:59}
  extendDeadline(): EXPIRED или просроченный CREATED → CREATED, dueDate=новый, reassigned=true
```

Важно: **транзакционная граница обрывается на границе сервиса**. `assign()` в app-контроллере — это два независимых HTTP-вызова (создание шаблона, затем назначение) без компенсации. `approve()` в task-service — одна локальная транзакция, но `grantReward()` внутри неё делает синхронный сетевой вызов в другую БД; откат локальной транзакции **не откатывает** уже применённое изменение баланса в user-service.

## 4. Причины перечисленных багов

### 4.1 Валидный дедлайн из `datetime-local` отклоняется сервером

**Корневая причина — конфликт двух независимых реализаций одной и той же задачи, добавленных в разное время:**

- `app/src/main/java/ru/taskhero/app/util/FormDateTimeParser.java:39` — `LocalDateTime.parse(value)` ожидает **сырую** строку без зоны/секунд, вида `"2026-08-27T18:00"` (это подтверждает и javadoc, и тест `FormDateTimeParserTest`, который прямо называется «регрессионный тест на баг «Ошибка назначения задания»»).
- `app/src/main/resources/static/js/app.js:117-132` — глобальный обработчик `submit`, навешанный на **все** формы страницы (`document.querySelectorAll('form')`), для **любого** `<input type="datetime-local" name="...">` создаёт скрытое поле с тем же именем и значением `new Date(input.value).toISOString()`, а исходное поле **дизейблит** (значит, в форму реально уходит только новое, ISO-Z-значение вида `"2026-08-27T15:00:00.000Z"`).
- `ParentController.assignTask()` (строка ~777) получает именно это ISO-Z значение в параметр `dueDate` и передаёт в `FormDateTimeParser.parseToInstant()`, который бросает `DateTimeParseException` (у `LocalDateTime.parse` нет ветки для `Z`/смещения) → перехватывается как `IllegalArgumentException` → пользователь видит «Некорректный формат дедлайна».

Это применяется к **каждому** назначению с дедлайном — не к отдельным случаям, а системно, при этом форма продления дедлайна (`ParentController.extendDeadline`, `/assignments/{id}/extend-deadline` в `TaskAssignmentController.java:433-437`) работает нормально именно потому, что там `Instant.parse(newDueDate)` — а этот метод как раз ISO-Z и ожидает. То есть исправление в `FormDateTimeParser` (сделанное, судя по докстрингу, для этой же самой ошибки) было впоследствии сломано добавлением глобального JS-конвертера, написанного, по всей видимости, под контракт `extend-deadline`.

### 4.2 При ошибке дедлайна шаблон/задание частично сохраняется

`ParentController.assignTask()`, строки 748-790: когда `templateId` не передан, метод **сначала** вызывает `taskServiceClient.createTemplate(...)` (строка 771, коммитится немедленно, отдельная HTTP-транзакция) и **только потом** парсит `dueDate` (строка 776-781). Если парсинг падает (см. 4.1, а он падает регулярно), возврат происходит `return redirectBack` **после** того, как `TaskTemplate` уже сохранён в БД task-service. Отката нет — это два разных HTTP-вызова без компенсирующей транзакции. Результат: осиротевший `TaskTemplate` без единого назначения, при каждой повторной попытке родителя — новый дубль.

### 4.3 Счётчик «На проверке» может включать неотправленные задания

`app/src/main/java/ru/taskhero/app/controller/ChildController.java:134-148`:
```java
List<TaskAssignmentDto> activeAssignments = taskServiceClient.getMyActiveAssignments(); // CREATED + SUBMITTED
long pendingCount = activeAssignments.size();
model.addAttribute("pendingCount", pendingCount);
```
`getMyActiveAssignments()` → `/assignments/my/active` → `TaskAssignmentServiceImpl.getActiveByChild()` → статусы `{CREATED, SUBMITTED}` (строка 154 сервиса). Переменная `pendingCount` затем рендерится в `child/dashboard.html:248-249` под лейблом **«На проверке»**. Так как CREATED — это ещё не отправленные ребёнком задания, счётчик «На проверке» фактически показывает «активные», что создаёт иллюзию задач на проверке, которых родитель не подтверждал, потому что ребёнок их даже не сдавал. На родительской стороне (`ParentController.sidebarPendingReviewCount`, строка 86-90) счётчик считается правильно — только по `getPendingReview()` (`status=SUBMITTED`), это асимметрия между детским и родительским представлением одного понятия.

### 4.4 Повтор по выбранным дням может появиться в другой день

Две независимые, но складывающиеся причины:

1. **Таймзона планировщика.** `RecurringAssignmentScheduler.java:40` — `ZONE = ZoneId.systemDefault()`, то есть зона JVM контейнера task-service. Ни в одном Dockerfile/compose нет `TZ=`, значит зона по умолчанию — UTC образа `eclipse-temurin`. При этом `today = LocalDate.now(ZONE)` (строка 53) определяет календарный день, по которому идёт сверка BYDAY-правила и создание `dueDate = today.atTime(23,59,59).atZone(ZONE)`. Для семьи, живущей восточнее UTC (а по уточнению заказчика — семьи из разных регионов РФ/СНГ, не только Москвы), граница дня в UTC сдвинута на несколько часов: около местной полуночи планировщик может ещё считать «вчера» или уже «завтра» — задание на конкретный день недели может быть создано в другой календарный день по местному времени семьи, чем ожидалось, и сдвиг разный для разных семей/регионов.
2. **`@Scheduled(fixedRate = 3600000)`** — это фиксированный интервал от старта приложения, а не привязка к конкретной минуте (не cron). Момент перехода через полночь UTC может оказаться где угодно в пределах часа после реального рубежа, что добавляет ещё до ~59 минут случайного сдвига поверх таймзонного.

Дополнительно стоит явное свидетельство расхождения намерений: миграция `task-service/.../010-store-due-date-as-utc-instant.xml` при конвертации старых `due_date` в `timestamptz` жёстко предполагает `Europe/Moscow` (`USING due_date AT TIME ZONE 'Europe/Moscow'`), тогда как весь текущий рантайм-код молча использует `ZoneId.systemDefault()` (де-факто UTC). Раз семьи-пользователи фактически живут в разных поясах РФ/СНГ, ни жёсткий `TZ=Europe/Moscow`, ни текущий UTC-по-умолчанию не решают проблему полностью — нужен явный часовой пояс на уровне семьи (см. раздел 7).

### 4.5 Повторное подтверждение может повторно начислить награду

Механизм, который *должен* защищать от этого — `@Lock(PESSIMISTIC_WRITE)` на `TaskAssignmentRepository.findByIdWithTemplateForUpdate` (строка 142-144), используемый в `approve()`. Это действительно закрывает **конкурентный** сценарий (два одновременных клика в одной транзакционной гонке блокируются на строке). Но он не закрывает более вероятный на практике сценарий — **последовательный retry после сетевого сбоя**:

- `TaskAssignmentServiceImpl.approve()` — это одна `@Transactional`-граница task-service. Внутри неё `rewardService.grantReward()` делает **синхронный Feign-вызов** в user-service (`RewardServiceImpl.java:46`, `PUT /children/{id}/reward`).
- Если Feign получает таймаут/обрыв связи **после** того, как `user-service` уже применил и закоммитил изменение баланса (`ChildServiceImpl.addReward`, обычный `@Transactional`, никак не связанный транзакционно с task-service), в task-service это выглядит как исключение → весь `@Transactional approve()` откатывается, включая только что записанный `status=APPROVED` — назначение возвращается в состояние `SUBMITTED`.
- Родитель (или фронтенд после ошибки) повторяет запрос «Одобрить» — статус снова `SUBMITTED`, никакой барьер это не остановит, `approve()` отрабатывает полностью и **повторно** вызывает `addReward` — баланс увеличивается второй раз за одно и то же выполненное задание.
- Усугубляет это то, что `RewardRequest` (`task-service/.../dto/RewardRequest.java`, `user-service/.../dto/RewardRequest.java`) **не содержит никакого идентификатора назначения/операции** — `ChildServiceImpl.addReward` безусловно прибавляет `exp`/`coins` при каждом вызове, дедупликации по `assignmentId` нет ни на одном уровне.

Итого: защита есть только от «двойного клика в один и тот же момент», а не от «повторного подтверждения» в широком смысле, который требует §3 `prompt.txt` («идемпотентно»). Тот же паттерн (чек статуса → списание баланса без блокировки строки) без вообще какой-либо защиты повторён в `ShopServiceImpl.approvePurchase()` (строки 199-229) — там нет ни `@Lock`, ни `@Version` на `ShopPurchase`/`Child`, то есть повторное подтверждение покупки потенциально ещё более уязвимо, чем подтверждение задания.

## 5. Риски миграции существующих данных

- **Расхождение таймзон исторических и новых `due_date`.** Миграция 010 предполагает, что все старые `due_date` были введены по `Europe/Moscow`; переход на хранение зоны семьи в модели должен учитывать, что часть строк уже сконвертирована с этим допущением, а часть новых строк писалась в предположении UTC (`systemDefault()`) — в самой таблице уже могут сосуществовать данные с разной фактической интерпретацией, и для семей не из московского пояса старые даты потенциально уже смещены неверно.
- **Осиротевшие `TaskTemplate` без назначений** (следствие бага 4.2) — если планируется миграция/чистка шаблонов или отчётность по «шаблоны → назначения», нужно заранее решить, что делать с накопившимся мусором (может быть значительным, так как баг воспроизводится системно).
- **`important`** — по `prompt.txt` §12 признак должен был перестать блокировать прогресс; в коде (`TaskAssignmentServiceImpl.approve()`, комментарий на строке 260-262) это уже сделано технически (поле сохранено, но не используется в расчётах) — риска нет, но стоит проверить фронтенд/фильтры, не осталось ли мест, где `important` всё ещё используется как блокировка.
- **`TaskStatus.EXPIRED`** — введён относительно недавно; любые аналитические/отчётные запросы, писавшиеся раньше только под `CREATED/SUBMITTED/APPROVED/REJECTED`, могут не учитывать эту ветку.
- **Нет `@Version` ни у одной сущности** — если в следующей итерации решите вводить оптимистичные блокировки для устранения гонок (раздел 4.5), это ALTER TABLE на «горячих» таблицах (`children`, `task_assignments`, `shop_purchases`) — нужно продумать zero-downtime миграцию (добавление колонки с default).
- Миграции сделаны как последовательные Liquibase changesets с сырым SQL (например, 010) — часть из них **не имеет** `rollback` блока, что затрудняет откат в проде при необходимости.

## 6. План автоматических тестов (по этапам §1–§9 из `prompt.txt`)

*(Этапы соответствуют разделам §1–§9 исходного ТЗ, а не произвольной нумерации.)*

**§2–3 Надёжность цикла и модель состояний**
- Интеграционный тест полного цикла: assign→submit→approve с проверкой итогового баланса и статуса на каждом шаге (частично покрыт `TaskAssignmentServiceImplTest`, `RewardServiceImplTest` — нужно свести в один сквозной тест через реальный `AbstractIntegrationTest`, а не только unit).
- Негативные переходы: `submit()` на `SUBMITTED/APPROVED/REJECTED/EXPIRED` → `ValidationException`; `approve()`/`reject()` на не-`SUBMITTED` → `ValidationException` (частично есть, проверить полноту матрицы 5×5 переходов).
- **Идемпотентность подтверждения**: тест, эмулирующий откат task-service-транзакции ПОСЛЕ успешного Feign-вызова (мок `UserServiceClient`, бросающий исключение после того, как отдельно проверено, что вызов дошёл) — сейчас такого теста нет, и с текущей архитектурой он **не может пройти**, пока не введён idempotency-key/outbox — это одновременно и тест, и спецификация будущего фикса.

**§4 Ошибка назначения задания**
- Тест, воспроизводящий именно тот дедлайн, который реально отправляет браузер после `app.js`-конвертации (`"2026-08-27T18:00:00.000Z"`), через `FormDateTimeParser` — **этого теста сейчас нет**; существующий `FormDateTimeParserTest` проверяет только «старый» сырой формат, поэтому регрессия из п.4.1 не поймана существующим тестовым набором.
- Тест на `ParentController.assignTask` (MockMvc/WebTestClient) с внедрённым сломанным дедлайном — убедиться, что шаблон **не создаётся**, если назначение не удалось (сейчас упадёт — это и есть баг 4.2).
- Матрица: один ребёнок / несколько детей, из готового / из своего задания — частично покрыто, нет явного теста на «несколько детей + не передан childId».

**§5 Упрощение формы создания задания**
- Тест, что при `templateId==null` создаётся полноценный редактируемый `TaskTemplate` (а не «облегчённая» сущность) — есть смысл проверить непосредственно через `TaskTemplateServiceImpl`.

**§6 Карточка задания для ребёнка**
- Контроллерный тест, что `TaskAssignmentDto` для карточки содержит все 4 обязательных поля (название, описание, срок, награда) даже когда `dueDate=null`/`description=null`.

**§7 Главный экран ребёнка**
- Тест на `ChildController` dashboard-метод: `pendingCount` должен считаться только по `SUBMITTED`, а не по «активным» — сейчас этот тест либо отсутствует, либо (если есть) фиксирует текущее неверное поведение как «ожидаемое» — стоит явно проверить.

**§8 Уведомления ребёнка**
- Тест на «уведомление о разблокировке на уровне N перестаёт показываться после достижения уровня N» — сейчас логика в шаблонах Thymeleaf, юнит-тестов, судя по списку тестовых файлов, нет.

**§9 Упрощение экономики (EXP системный)**

## 7. Рекомендуемая последовательность изменений с зависимостями

Приоритет багов подтверждён заказчиком: **А → В → Б**, то есть:

1. **Унифицировать разбор дедлайна между app.js и `FormDateTimeParser`** (баг А, п.4.1) — без этого шага любые последующие изменения в формах с дедлайном (шаблон, назначение, продление) будут наследовать один и тот же баг. Варианты: либо убрать `FormDateTimeParser`/перейти на `Instant.parse` везде и полагаться на JS-конвертер (тогда логика зоны — на стороне браузера, что и точнее), либо исключить `dueDate`-поля из глобального JS-обработчика и оставить `FormDateTimeParser`. **Это блокирует** следующий пункт.
2. **Переставить порядок операций в `assignTask`** (баг А, п.4.2): валидировать/парсить `dueDate` **до** `createTemplate`, либо (лучше) вынести создание шаблона и назначения в одну транзакцию на стороне task-service (один эндпоинт «создать-и-назначить»), чтобы не было двух независимых HTTP-вызовов с точкой отказа между ними.
3. **Ввести idempotency-key для `grantReward`/`addReward`** (баг В, п.4.5) — самый архитектурно значимый пункт: передавать `assignmentId` (или `assignmentId+reviewedAt`) в `RewardRequest`, на стороне `user-service` вести отдельную таблицу применённых начислений с уникальным ограничением на этот ключ, либо хранить `rewardAppliedAt`/`sourceAssignmentId` прямо в истории. Без этого «идемпотентность подтверждения» из §3 ТЗ физически невозможна. Это же решение стоит одновременно применить и к `ShopServiceImpl.approvePurchase` (добавить `@Lock`/уникальность), так как там защиты нет вообще.
4. **Хранить часовой пояс семьи явно в модели `Parent`** и передавать его во все Instant-конвертации вместо `ZoneId.systemDefault()` — это разблокирует корректную работу `RecurringAssignmentScheduler` (п.4.4) для семей из разных регионов РФ/СНГ и синхронизирует поведение с уже принятым в БД (миграция 010) допущением о зоне для старых данных.
5. **Исправить `pendingCount` на детском дашборде** (баг Б, п.4.3) — тривиальное точечное исправление (использовать `SUBMITTED`-выборку вместо «активных»), не имеет зависимостей от остального; по приоритету идёт последним из трёх багов, но технически можно сделать в любой момент после стабилизации статус-цикла (пп.1-3), чтобы не тестировать на движущейся цели.
6. Только после 1-4 — переход к P1/P2 пунктам из `prompt.txt` (карточка задания, главный экран, экономика EXP, наведение сложности) — они не зависят от найденных багов технически, но UX-тестирование на сломанном фундаменте («Ошибка назначения задания» до сих пор не исправлена системно) даст ложные результаты.

## 8. Вопросы, снятые в ходе диалога с заказчиком

- **Часовой пояс.** Реальные семьи-пользователи живут в разных регионах РФ/СНГ (не только Москва) → фикс дат/повторов должен хранить часовой пояс семьи в модели, а не жёстко фиксировать `TZ=Europe/Moscow` на контейнерах (см. п.7.4).
- **Приоритет багов.** А (ошибка назначения задания при дедлайне + осиротевшие шаблоны) → В (повторное подтверждение может задвоить награду) → Б (детский счётчик «На проверке» включает неотправленные задания) — отражено в последовательности раздела 7.
